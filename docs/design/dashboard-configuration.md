# Dashboard configuration

Repository assessment and implementation plan, 2026-10-19. This note distinguishes the first configuration phase from the provider work that remains. Administrator instructions are in [the configuration runbook](../runbooks/dashboard-configuration.md).

## Repository assessment

StudyHub already runs one application for many schools. Host resolution selects a school, `TenantDb` opens transactions with its tenant context, and PostgreSQL row-level security isolates tenant-owned rows. School-specific functionality belongs in shared modules with per-school configuration and authorization; it does not require a copied application or a school-specific branch.

| Existing component                      | Reuse                                                                                           | Gap before this phase                                                                                                                                      |
| --------------------------------------- | ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `packages/contracts/src/settings.ts`    | Zod content, general and commerce schemas and defaults                                          | Settings have no common inherited-value view or reviewed activation workflow.                                                                              |
| `tenant_setting`, `platform_setting`    | Existing school and platform configuration storage                                              | Platform defaults and enforceable school-override restrictions are missing for content settings.                                                           |
| `CommerceSettingsService`               | School admin permission checks, validation and audit                                            | The legacy settings PATCH writes immediately; representative managed keys must obey the same restrictions through every write path.                        |
| Branding editor                         | School-owned draft, publish, history and rollback pattern                                       | This specialized workflow does not provide a general settings lifecycle.                                                                                   |
| `tenant_feature`, plans, `readFeatures` | Existing entitlement, override and school-switch calculation                                    | No dependency graph, time-based rollout scheduler or comprehensive background-job enforcement inventory exists.                                            |
| Console authentication and audit        | Separate platform realm, MFA and recent TOTP reauthentication                                   | New sensitive platform changes must reuse these controls.                                                                                                  |
| `SecretBox`, `PaymentVault`             | AES-256-GCM with purpose-bound additional data; payment envelope encryption                     | A general integration credential store and rotation lifecycle do not exist.                                                                                |
| `ObjectStorage`, `S3ObjectStorage`      | Private S3-compatible storage, signed URLs and school key prefixes                              | API and worker choose one environment-configured adapter at startup. Objects do not record a storage location. Changing that adapter can strand old files. |
| Payment accounts                        | Owner-only credential entry, masked views, test-before-activate and original account references | Only the development fake is fully wired. Other providers must complete validation and adapter work.                                                       |

Existing uncommitted hardening and recovery work remains part of the repository baseline. In particular, the document backup and recovery adapters do not constitute dashboard storage switching or automatic object migration.

## Phased implementation

1. **First end-to-end phase:** use three existing content settings to establish typed platform defaults and restrictions, effective school values, drafts, review, activation, history, eligible reverts, override reset and an allowlisted nonsecret `.env` import preview. Keep effective school values in the existing `tenant_setting` rows and route runtime consumers through their shared reader. Reuse school permissions, console reauthentication and both audit realms.
2. **Feature enforcement:** retain `tenant_feature` and plan entitlements. This session adds guards for instructor applications, anonymous catalogue/lesson preview access, queued full exports and runtime white-label branding, plus an explicit revenue-sharing dependency in school switches and console overrides. A complete entry-point/job inventory and plan-change transition policies remain open.
3. **Storage provenance:** persist an immutable storage-location reference for original objects, derivatives and exports; backfill legacy objects to a captured deployment location; route every reader, worker and recovery path by that reference. Verify that old assets survive a switch before exposing activation.
4. **Credential and storage lifecycle:** add encrypted integration drafts, write-only credentials, safe connection testing, version-bound test results and platform storage activation. Add R2 and the current local S3-compatible provider to the dashboard only after their validation and operational tests exist.
5. **Further integrations and migration:** extend adapters only for actual supported services; implement a separately reviewed storage-copy operation with checkpoints and verification. Evaluate email, video, malware scanning and payment changes independently.

The first phase does **not** provide R2 dashboard activation, saved storage credentials, secret imports, object migration, a new email/video/payment adapter or a general feature dependency engine. Those are incomplete work, not disabled working features. Provider connection testing, secret masking and asset access after a real storage switch still require their own tests in the corresponding phase.

## Ownership and precedence

| Configuration class     | Owner and scope                                  | Examples                                                                                                | Application                                                                                  |
| ----------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Platform policy         | Authorized platform administrators               | Platform defaults and locks for the three managed content settings                                      | Database-backed; next relevant request or operation after activation.                        |
| School settings         | Authorized administrators of the resolved school | Permitted content overrides, branding, supported locale selection                                       | School-scoped database rows; no client-selected tenant identifier.                           |
| Integration credentials | Must be explicit per adapter                     | Shared storage should begin platform-owned; payment merchant accounts remain school-owned               | Future storage credentials require encryption and a lifecycle separate from public settings. |
| Deployment/bootstrap    | Deployment operators, outside dashboard          | Database URLs, root encryption keys, process binding, proxy trust, console hosts and startup identities | Process restart or deployment; never imported by the dashboard.                              |

For the three managed content values, resolve in this order:

1. Take the typed code default from the existing shared content schema.
2. Apply the activated platform default.
3. Apply a validated school override only where the platform permits it.
4. Apply a platform lock as the final restriction; a saved school override cannot defeat it.

The editor must distinguish the platform default, the saved school override, whether overriding is permitted, and the final effective value. A reset removes the school's override, so future platform-default changes are inherited. A platform lock does not erase an existing override: the editor must show that it is currently ineffective. Features and plan caps are additional authorization constraints; changing a setting must not grant a feature or increase an upload or usage limit.

Existing school rows remain school overrides during adoption, preserving their intended values. A missing row inherits. Each accepted value is validated by the existing schema; malformed stored values must not be presented as a valid override. Configuration schema versions describe data shape; revision digests identify edits. They are different concepts. An upgrade must have an explicit reader or migration for each prior supported schema version, reject unknown future versions, and validate historical snapshots again before restoration. Do not reinterpret an old snapshot silently when a setting changes meaning.

The shared contract is `packages/contracts/src/configuration.ts`. Version 1 uses existing tables: `platform_setting` key `configuration.contentDefaults` stores `{ schemaVersion: 1, values, lockedKeys }`; each school's overrides remain the three original `tenant_setting` keys. Each scope stores its draft under `configurationContentDraft`, which satisfies the existing school-setting key constraint. Activated history is appended to its audit log as `configuration.activated` snapshots. No new database migration is needed for this phase.

Legacy scalar override rows are adopted directly after validation; a missing platform document means the version 1 empty-default envelope. Malformed active data or an unknown schema version fails closed with `SERVICE_UNAVAILABLE` rather than silently activating defaults. Before a version 2 deployment, implement and test the explicit version 1 upgrade, retaining the previous snapshot and a rollback plan. An invalid version 1 envelope currently requires a reviewed operator repair of the affected database value. A dedicated repair CLI, automatic upgrader and dashboard repair flow are not implemented.

The school API base is `/api/v1/admin/configuration`; the console backend base is `/console/configuration` (proxied through `/api/console/configuration` in the browser). Both support `GET` for the editor view, `PUT /draft` for the complete desired override set, `POST /activate` for the reviewed draft and `POST /import-preview` for input validation. An omitted value in the submitted full draft means reset/inherit rather than leaving the saved override unchanged. Activation binds a UUID `draftId` and SHA-256 `expectedRevision` to the current scoped snapshot and platform document. Advisory locks serialize changes, and stale revisions are refused. Platform configuration is restricted to `PLATFORM_OWNER`, with recent console TOTP reauthentication for activation. School configuration uses `admin.access` and the existing support-session write rules.

The revision is a canonical content digest, not an increasing counter: it includes scope, school id where applicable, schema version, ordered active values, platform defaults and deduplicated/sorted locks. Saving or replacing a draft assigns a new draft UUID without changing the active revision. Activation checks both the current active digest and the saved draft's base digest, then validates the exact UUID; editing defaults or restrictions makes affected school drafts stale. Two configurations with identical effective stored snapshots can have the same digest even if intermediate changes occurred. The activation history exposes snapshots from the latest 20 activation records and the baseline before the earliest retained record, allowing the first activation to be reverted. It does not include historical legacy PATCH events. The baseline timestamp identifies the activation it preceded; its original author is unknown.

## School-specific features

Develop a capability once in its shared domain module. Add an explicit key only when the capability exists, use the existing feature resolver and let an authorized platform administrator grant it to selected schools. A school can turn on an available implemented feature in its existing feature screen. Other schools keep their independent plan, override and switch state.

The current rule in `tenancy/domain/features.ts` is:

```text
effective = implemented
            AND platform override is not REVOKE
            AND (plan grants feature OR platform override is GRANT)
            AND school switch is on
```

A missing plan currently preserves legacy access to built features; a missing grant in an assigned plan does not grant the feature. Most school switches default on; `instructorRevenueShare` defaults off. `customDomain` and `certificates` are explicitly unimplemented and always ineffective; the console now rejects `GRANT` requests for them. A platform `GRANT` permits access but does not override the school's off switch. A platform `REVOKE` wins.

Plans define commercial entitlement and usage caps. School configuration chooses permitted behavior within those rights. Platform policy may restrict or grant a capability. None of these can manufacture an adapter, translation, workflow or domain behavior that has not been developed.

For gradual rollout, grant a completed capability only to the pilot school while keeping other schools ungranted or revoked as appropriate. Record the reason and verify both schools. Scheduled, percentage or cohort rollout tooling is future work. Do not invent a second independent flag system for it.

This session closes these specific backend gaps:

| Capability               | Delivered enforcement                                                                                                                                                                                             | Preserved behavior                                                                                                                                                                                          |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `instructorApplications` | `courses/application/instructors.service.ts` requires the feature for non-instructor application drafts and submission, and reports invitation-only onboarding when unavailable                                   | Approved instructors can still maintain their profiles; submitted application data is retained.                                                                                                             |
| `publicCatalog`          | `courses/application/catalogue.service.ts` and `learning/application/access.ts` require authentication for anonymous catalogue and lesson-preview access when the feature is off or the catalogue is members-only | Existing enrolled learners, course owners and administrators retain their normal authorized learning access. The flag does not disable the entire school catalogue for signed-in members.                   |
| `dataExport`             | `admin/application/exports.ts` rechecks the school's feature before starting a queued `TENANT_FULL` export                                                                                                        | If revoked, the export is marked `FAILED` with `FEATURE_NOT_ENABLED`, without provider I/O or repeated queue retries. This is a start-of-work check, not continuous cancellation after an export has begun. |
| `whiteLabel`             | `tenancy/infra/tenant.repository.ts` caps published bootstrap branding at render time after revocation                                                                                                            | The saved preference remains; the badge is required while access is unavailable.                                                                                                                            |
| `instructorRevenueShare` | `tenancy/domain/features.ts` declares `paidCourses` as a dependency; school switch and console override requests validate it under the same per-school advisory lock                                              | Enable paid courses before enabling/granting sharing; disable sharing before disabling/removing effective paid-course access. Existing financial records are not rewritten.                                 |
| Unimplemented features   | `console/application/console-tenants.service.ts` refuses grants for `customDomain` and `certificates`                                                                                                             | Their existing always-off resolver behavior remains.                                                                                                                                                        |

School switches continue to write `feature.switched` school audit entries. Console overrides continue to write `tenant.feature_override` in platform and school audit trails, including the reason. These controls use the original feature mechanism rather than a second flag store.

Dependencies must be explicit server rules. Payment-method settings remain constrained by the active account's detected capabilities, white-label branding requires its entitlement, and upload size settings cannot exceed plan caps. New dependencies should be validated both on configuration change and at the operation that needs them. If a prerequisite becomes unavailable, return an actionable unavailable state and preserve existing data. A future generic dependency graph must reject cycles and must not silently enable paid prerequisites.

Two dependency and financial gaps remain explicit. Plan edits and school plan reassignment do not yet apply the new dependency transition checks; they can leave an inconsistent sharing/paid-course combination. The runtime feature-map formula does not automatically cascade dependencies to repair that state. Separately, `commerce/application/settlement.ts` currently checks sharing availability and reads commission/refund settings when payment is confirmed. Checkout does not freeze all of those terms in an immutable sharing snapshot, so a feature or setting change between checkout and confirmation can change the eventual split. A dedicated financial design must define and persist the relevant sale terms; do not present this session's switch validation as solving that gap.

Check feature access in domain/application entry points, including direct API access. Jobs that initiate new feature-controlled work must resolve the relevant school's current rights before acting. Jobs completing already accepted financial work, scanning an upload or maintaining integrity need an explicit continuation policy: a revoked UI feature must not strand payments, bypass malware checks or corrupt usage accounting. Hidden navigation is presentation, not enforcement. A complete inventory of these job policies remains phase 2 work.

## Drafts, review and history

The managed editor separates candidate changes from live values. Saving a draft validates its supported keys and types but does not activate it. Review compares the candidate with the current effective configuration and describes the operational effects above. Activation must revalidate permissions, schema version, current platform policy and the exact reviewed revision inside the committing transaction. A stale review must be refreshed rather than silently overwriting another administrator's changes.

Activation, eligible revert and override reset produce new revisions and audit entries with actor, scope, time, reason and nonsecret changed values. Revert means applying a compatible earlier configuration as a new change under today's policy. It cannot reverse external messages, payments, uploads, course publications or data migrations. Old drafts/history must not bypass newly enforced locks. The legacy immediate settings endpoint must share the managed-key enforcement or reject those keys; the new UI alone cannot establish policy.

## Import and credential boundary

The first phase accepts only the recognized **nonsecret** aliases `SCHOOL_CATALOG_VISIBILITY`, `SCHOOL_COURSE_REVIEW_REQUIRED` and `SCHOOL_DOWNLOADS_ALLOWED_DEFAULT` for its three managed settings. Import parses text as data, validates types, reports unsupported keys without echoing their values, and creates a preview before a draft can be saved. It does not run shell code, expand environment variables, evaluate substitutions, write the deployment `.env`, or retain the raw uploaded file. A mixed file containing unsupported or bootstrap keys must be corrected before acceptance; an unsupported line rejects the preview rather than partially applying preceding valid lines.

The implemented grammar accepts UTF-8 text up to 32,768 bytes, strips a leading BOM, ignores blank and comment-only lines, accepts an optional literal `export ` prefix, and requires recognized uppercase `KEY=value` assignments. Values may be single- or double-quoted on one line; quotes do not enable escape processing, substitutions or multiline values. Unquoted trailing comments require whitespace before `#`; quoted values may be followed by a comment. Duplicate keys, malformed assignments/quotes, null characters, empty imports, unsupported keys and invalid values are rejected. Catalogue values are exactly `PUBLIC` or `MEMBERS_ONLY`; booleans are lowercase `true`/`false`. Errors identify the line/key, never the rejected value. The preview response contains only validated, nonsecret entries.

In the browser, choosing **Use preview in draft** merges recognized imported values into current local edits, preserving values omitted from the file. School-locked imported entries are displayed as excluded and cannot replace the corresponding saved override through that action. A later draft save is still the complete replacement set and remains subject to backend lock/revision validation. The same alias allowlist is used for platform defaults and school overrides; authentication selects the scope and a file cannot set locks.

Credential import and dashboard credential entry are future work. Do not paste a real deployment `.env` into the first-phase editor. Keys such as `DATABASE_URL_APP`, `DATABASE_URL_MIGRATOR`, `IDENTITY_ENCRYPTION_KEY`, `PAYMENT_ENCRYPTION_KEY`, process/host/proxy settings and storage/SMTP/scanner credentials remain outside its allowlist.

The existing secret-management primitives are suitable building blocks: `platform/security/secret-box.ts` uses AES-256-GCM with purpose-bound additional authenticated data; `commerce/infra/payment-vault.ts` gives each payment account a random data key sealed by a deployment key. A future integration vault should bind ciphertext to its scope, integration id, version and purpose. Its root key or secret-store identity must remain outside the database and dashboard. Store key identifiers to support controlled rotation; retain the keys needed to decrypt historical locations during a safe transition.

Saved credentials must be write-only. Responses, previews, audits and history show only credential presence and an explicitly safe masked hint. Replacement or revocation must invalidate connection-test evidence. Reauthentication is required for entry, replacement, revocation and activation; the console already provides recent TOTP verification. Equivalent school-sensitive controls must be established before adding new school-owned credential flows. Never log imported content, request bodies, raw provider errors, signatures or decrypted configuration. This phase broadens logger redaction for configuration and credential fields. Redaction remains a defense in depth, not permission to log secrets; a future adapter must account for all of its sensitive field names.

## Safe storage activation design: future phase

Keep `ObjectStorage` as the bytes/signing port and add a resolver above it. A persisted storage location identifies provider, endpoint/region, bucket and credential reference. An asset refers to the location used for its original object and its derivative. Exports and recovery metadata also need a location reference. The object key remains school-prefixed and private. Do not repurpose `asset.provider`, which currently identifies the managed video provider.

Capture the current deployment location and backfill existing object rows before changing routing. Avoid a permanent “missing location means current active provider” fallback: the meaning would change on every activation. Freeze the selected location when reserving an upload slot; an in-flight upload and its later scan/derivative work must finish against that location even when a new writer becomes active. Derivatives should use the original location unless an explicitly persisted separate location is supported.

Route all reads and writes by persisted location: `MediaService`, `process-asset`, branding previews/redirects, Studio covers, lesson downloads, full exports, export downloads, recovery staging and purge. The worker and API must consult the same activated configuration revisions; building adapters once at process boot is insufficient for immediate activation. Begin with request/job-time resolution and a bounded version-keyed cache, then add invalidation only if needed. Show “worker refresh required” in the UI if a future implementation actually needs one.

Retain historical locations and working credentials for reads and already issued uploads. Retiring a writer is different from revoking the ability to read its objects. Refuse unsafe deletion of a referenced location. Offboarding must enumerate every school location before deleting metadata; otherwise a purge can orphan objects in a retired bucket. Backup stores and their protection policies are distinct from live storage.

R2 can reuse the AWS SDK v3 S3 adapter: Cloudflare documents account-specific HTTPS endpoints and `region: auto`. Browser presigned PUTs need matching content types and bucket CORS for the school's origin. A successful signature calculation alone is not a connection test because signing occurs locally. See the official [SDK v3 example](https://developers.cloudflare.com/r2/examples/aws/aws-sdk-js-v3/) and [presigned URL documentation](https://developers.cloudflare.com/r2/api/s3/presigned-urls/), checked 2026-10-19. This establishes adapter feasibility, not verified dashboard support.

For a future R2 form, accept a validated account id and construct its official endpoint server-side. Use bucket-scoped credentials with the object operations required by the implemented lifecycle; Cloudflare's [S3 setup](https://developers.cloudflare.com/r2/get-started/s3/) and [authentication guidance](https://developers.cloudflare.com/r2/api/tokens/) describe access-key credentials and bucket scoping. Keep bucket provisioning, CORS changes and backup permissions as explicit operator tasks unless separately implemented and authorized.

A connection test must have an overall deadline, bounded SDK retries, no redirect to an unvalidated host, sanitized error codes and rate limiting. A bounded create/read/delete probe under a dedicated test prefix can verify the required object capabilities without touching real assets; disclose any probe cleanup failure. Validate endpoint ownership and scheme; reject userinfo, unsafe ports, loopback, link-local, metadata and private-network destinations for production dashboard connections. Generic S3 endpoints additionally need safe DNS resolution and rebinding-resistant egress enforcement. The local SeaweedFS exception must be narrowly deployment-owned and development-only. Do not send credentials to an arbitrary URL supplied in a dashboard form.

Bind a successful test to provider, normalized configuration digest and credential version. Activation must verify that exact evidence is still current; failed or stale tests must leave the existing writer active. Runtime provider failure must surface an unavailable error with retry guidance, never fall back to the development store.

Object migration is a separate operation with immutable source/destination locations, an object manifest, per-object status and attempt count, resumable checkpoints and bounded retries. Copy originals and derivatives, verify byte length and a stored checksum, then update references atomically with optimistic concurrency. Retain source objects and a recovery manifest; never automatically delete them. Report progress and failed objects. Reverting the writer does not move any objects back, and rolling back configuration does not undo a completed copy.

Payments remain separate. `payment.paymentAccountId` and provider fields preserve original routing for transaction status, webhooks and refunds; disabling an account intentionally retains its records. New sales may use a new activated account while old transactions continue with their originating provider. Do not rewrite ledger records, payouts or old account associations during a storage or settings change.

## Adding functionality safely

For a new configurable setting, first confirm a runtime consumer exists. Extend the shared Zod contract and typed defaults, choose ownership, override policy and effect timing, add it to the managed allowlist, extend persistence/version upgrade handling, and wire all readers/writers to the same resolver. Add inheritance, lock, reset, unauthorized and cross-school tests. Expose it in the editor only after the backend behavior works. Add an import alias only when that key is safe and supported in the same scope.

For a new feature, implement its module behavior and permissions, register its key in the shared feature contract, add plan/default rules and an explicit dependency policy, and enforce it in every relevant API and job entry point. Keep unfinished work in the unimplemented set. Grant a completed feature to one local pilot school through the existing platform override; independently verify that another school cannot use it through direct API access.

For a new provider, implement the existing domain port before listing it as supported. Add a strict provider-specific schema, scoped encrypted credential ownership, bounded connection validation, production-safe failure behavior, timeouts/retries and webhook verification where relevant. Test cross-school isolation and historical-provider routing. Recheck current official provider documentation at implementation time; an S3-compatible label alone does not prove every needed operation works.

## Verification boundaries

First-phase checks must cover inherited/default/locked values, unauthorized platform and school writes, cross-school draft/history isolation, invalid and unsupported imports, stale or failed activation, reset and eligible revert. Runtime tests must prove catalogue access uses the resolved value and new-lesson defaults affect only the intended school. Demonstrate one local school's changed setting while another retains its own configuration. Record actual commands and results in the handoff; this design note does not claim every check has passed.

Later phases must add credential masking/no-log tests, reauthentication tests, unsafe endpoint rejection, test-evidence invalidation, connection failure retaining the old writer, queued-upload processing after activation, reads of old originals/derivatives/exports after switching, and migration interruption/recovery. The current object-recovery tests cover bounded restoration, not these new switching guarantees.
