# M8 design note: commerce, payment accounts and ledger

- **Status:** IMPLEMENTED (2026-10-15). Items marked **PROPOSED** were decided during implementation and need client confirmation.
- **Baseline:** M7 commit; blueprint revision 4 (03 F24–F29, F45, §9.2, §9.5 W1–W6; 04 §7.1, §7.2, §17.10; 05 §3.6, §3.7, §4.8, §4.9, §5, §8.2 `payment_account`, `tenant_setting`; 06 S-L08–S-L11, S-T07, S-T11, S-T12, S-AD02, S-AD04, S-AD05, S-AD09, S-AD15; BR-07 to BR-15, BR-33, BR-35, BR-36, BR-54, BR-55, BR-62, BR-63).
- **Scope (07 §M8):** F24–F29 and F45 per school; the payment capability model and capability-limited payment settings; workflows W1–W6.

## 0. Gates and open decisions

- **No real payment provider (Q-PAY-3).** None is approved, so only the **fake adapter** exists (04 §17.10). It is refused in production by configuration, like the fake video provider. A real adapter is a new class behind the same port once the client approves a provider in writing (10 §11).
- **Money flow (Q-TEN-4 / Q-BIZ-1 / Q-PAY-1) is still a recommendation.** M8 builds the recommended option (a): each selling school connects **its own** merchant account and the platform never holds school money (ADR-0019, Proposed). Option (b) would change the ledger and payouts. **PROPOSED, needs confirmation.**
- Instructor commission, refund window and payout schedule (Q-BIZ-2), and network prefixes (Q-PAY-2), use the blueprint defaults as settings. Tax lines (Q-LEG-3) are optional seller fields with no tax computed.

## 1. Data model (migration 0008)

| Table                         | Notes                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `payment_account`             | Per school. Provider, label, status `PENDING / ACTIVE / DISABLED / FAILED_TEST`. Credentials and webhook secret are **envelope-encrypted**: each row has its own data key (AES-256-GCM), sealed by the key-encryption key `PAYMENT_ENCRYPTION_KEY`, with the row's school and id bound as AAD. Masked hint only. `capabilities` jsonb recorded by the connection test. At most one `ACTIVE` per school (partial unique).    |
| `order`, `order_item`         | Snapshot of price, currency, title and instructor (BR-08). One item per order (application rule). `order_item.commission_bps` is set at confirmation when revenue share applies (W2), so the ledger check knows what to expect.                                                                                                                                                                                             |
| `payment`                     | Per order and account (`payment_account_id` NOT NULL). `reference` is our random UUID, unique per school (every index leads with `tenant_id`, T-ISO-03; webhooks route by account, not by reference). The number is stored encrypted (same box) plus a masked copy. One `INITIATED / PENDING` payment per order (partial unique, BR-36). State machine of 05 §3.6. Reconciliation schedule: `next_check_at`, `check_count`. |
| `payment_event`               | Raw verified webhook events, unique `(tenant_id, payment_account_id, provider_event_id)`.                                                                                                                                                                                                                                                                                                                                   |
| `refund`                      | Full refunds only. `mode PROVIDER / MANUAL`, `status PROCESSING / SUCCEEDED / FAILED`, reason, references.                                                                                                                                                                                                                                                                                                                  |
| `receipt`, `receipt_sequence` | Number `{PREFIX}-{year}-{seq:06}`, gap-free per school per year: the sequence row is incremented inside the confirmation transaction (BR-33, BR-55).                                                                                                                                                                                                                                                                        |
| `idempotency_key`             | PK `(tenant_id, membership_id, key)`; route, request hash, stored response; purged after 24 h.                                                                                                                                                                                                                                                                                                                              |
| `ledger_entry`, `payout`      | 05 §3.7, per school. `CHECK gross − fee − commission = net`. A trigger rejects changes to amounts, type and links; the runtime role has no DELETE. Status only moves forward. `unique(order_item_id) WHERE type = 'SALE'`.                                                                                                                                                                                                  |
| `payout_method`               | An instructor's payout details (encrypted) with a display hint and a default (BR-04, S-T12). Needed only with revenue share.                                                                                                                                                                                                                                                                                                |
| `ledger_check`                | The result of each daily ledger check (W6): totals and mismatches.                                                                                                                                                                                                                                                                                                                                                          |
| `tenant.receipt_prefix`       | 2–8 upper-case letters or digits, optional: receipts fall back to a prefix made from the slug (`ACME`).                                                                                                                                                                                                                                                                                                                     |

Definer functions (routing data only, 04 §17.4; added to the T-ISO-03 inventory): `resolve_payment_account(id)` → `(tenant_id, provider)`; `due_ledger_checks(limit)` → `tenant_id` of active schools with sales and no check in the last 24 h; `current_school_host()` → the current school's primary host, for links in emails the worker sends. Reconciliation, order expiry and ledger release need no cross-school sweep: each is a delayed outbox row written in the same transaction as the record it watches (as M7 does for auto-submit).

## 2. Payment provider port and the fake adapter

- `PaymentProvider` (per account, never global): `testConnection`, `startPayment` (mobile-money push or hosted card page), `getStatus` (authoritative status, amount, currency, fee), `refund`, `verifyWebhook` (raw body, constant-time) and `capabilities`.
- **Capability model (BR-62):** `{ mobileMoney: { networks[] } | null, card, refundApi FULL / PARTIAL / NONE, statusQuery, transactionListApi, disbursementApi, currencies[], webhookSigning }`. The connection test records what the account actually has. Missing optional capabilities fall back as specified: no refund API → manual refunds; no disbursement API → recorded payouts.
- **Fake adapter (development and tests only):** credentials `{merchantId, apiKey, webhookSecret, profile}`. `profile` picks a capability combination (`FULL`, `MOBILE_ONLY`, `CARD_ONLY`, `NO_REFUND_API`, `PARTIAL_REFUND`), so every combination can be tested (AC 8). An `apiKey` starting with `bad` fails the test and every call (AC 3). The provider's own state lives in a separate `fake_provider` schema (the "provider's database"; no school data, unused in production).
  - **Simulated phone:** a mobile-money charge stays pending until the learner presses "Approve" or "Decline" on a clearly labelled simulated phone on the payment page. The development endpoint then sends a signed webhook, as the provider would. Sandbox numbers ending in `2222` (insufficient funds), `3333` (declined), `4444` (no answer), `5555` (paid amount differs) and `9999` (provider rejects the request) script other outcomes.
  - **Card:** a fake hosted page at `/api/v1/dev/fake-pay/{reference}` with Pay or Decline, then a signed webhook and a redirect to the return URL.
- **Circuit breaker per account:** 5 failures in a minute open it for 30 s, so one school's bad credentials never block another (AC 3).

## 3. Workflows

| Workflow                  | Behaviour                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| W1 Payment (F25, F26)     | `POST /orders` (Idempotency-Key): verified email, published paid course, not the caller's own (BR-31), not already enrolled (BR-07), `paidCourses` on, an active payment account; reuses a pending order (BR-35). `POST /orders/{id}/payments` (Idempotency-Key): only methods that are enabled **and** supported; a new payment cancels the previous pending one locally (BR-36). Webhook → verify with **that account's** secret → store the event → outbox → worker re-queries the provider → one transaction: payment `SUCCEEDED`, order `PAID`, `PURCHASE` enrolment, ledger lines, receipt number, emails. The return URL only triggers a re-query (F25 AC 1). |
| Exceptions (BR-10, BR-11) | A wrong amount or currency, a second success on a paid order, or a success after the learner was enrolled another way → `NEEDS_REVIEW`, no access, the school's exceptions queue. Admin: re-check, **Accept** (grants access, audited) or **Refund**.                                                                                                                                                                                                                                                                                                                                                                                                                |
| W2 Commission (BR-14)     | Only with `instructorRevenueShare`: `SALE` entry with commission = `instructorCommissionBps` × gross (half-up to the ngwee), fee = the provider's fee if reported, net = remainder; `PENDING` until `available_at` = paid + `refundWindowDays`.                                                                                                                                                                                                                                                                                                                                                                                                                      |
| W3 Payout                 | Admin selects an instructor's `AVAILABLE` entries, pays outside StudyHub and records reference and date; the amount must equal the entries' net sum and be positive; the entries become `PAID`; the instructor is emailed. Every available **negative** entry must be included (AC 7).                                                                                                                                                                                                                                                                                                                                                                               |
| W4 Refund (F28, BR-13)    | Admin, Idempotency-Key, reason. With `refundMode = PROVIDER_API` and a refund API: the provider is called first, then one transaction. Otherwise a manual refund with the reference of the money returned. The transaction: refund `SUCCEEDED`, payment and order `REFUNDED`, enrolment `REVOKED`, `REFUND_REVERSAL` entry, emails. A reversal follows its sale's status (pending with it, else available), so a refund after payout leaves a negative available balance (AC 7). The window (7 days, ≤ 30 % progress) is guidance shown to the admin, not enforced.                                                                                                  |
| W5 Reconciliation         | A delayed outbox row 2 min after the payment starts. The worker re-queries the provider; while still pending it reschedules with backoff (2, 4, 8 … min) up to 24 h, then marks the payment `EXPIRED`. Late successes on `CANCELLED` or `EXPIRED` payments, or on expired orders, are still honoured.                                                                                                                                                                                                                                                                                                                                                                |
| W6 Ledger check           | Hourly the worker asks `due_ledger_checks()` for schools not checked in 24 h, and runs the check in each school's context: every revenue-share order item has exactly one `SALE` of its price, every successful refund of such an item exactly one matching reversal, and payouts equal their entries. A mismatch stores the result, emails the school's owners and logs a platform warning with the school id only.                                                                                                                                                                                                                                                 |
| Order expiry              | A delayed outbox row at `expires_at` marks a still-pending order `EXPIRED`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |

## 4. Settings (BR-62) and publishing (BR-04, BR-54)

- New commerce settings: `enabledPaymentMethods` (`MOBILE_MONEY`, `CARD`), `orderExpiryMinutes` (30), `refundWindowDays` (7), `refundMode` (`MANUAL`), `instructorCommissionBps` (2000), `payoutSchedule` (`MONTHLY`, shown only), `receiptSeller {legalName, address, taxId}`, plus the existing `minPaidPriceMinor`. `PATCH /admin/settings` accepts this group now (M9 adds the others). Enabling a method or refund mode the active account doesn't support → `422 PAYMENT_METHOD_NOT_SUPPORTED`. Each change is audited.
- A course can be **published** with a price only when `paidCourses` is on, the school has an `ACTIVE` account (BR-54) and, with revenue share, the instructor has a payout method (BR-04). Checkout refuses with `422 COURSE_NOT_PURCHASABLE` when the account is later disabled.

## 6. PROPOSED decisions

1. **Money flow option (a)** (§0) until the client confirms Q-TEN-4.
2. **Fake provider state in a `fake_provider` schema,** plus a simulated phone and a fake hosted card page, both refused in production.
3. **Scheduling through delayed outbox rows** (reconciliation, order expiry, ledger release) instead of cross-school sweeps; only the daily ledger check discovers schools, through a definer function.
4. **`instructorRevenueShare` is off by default** (a school's own switch defaults to off for this feature only), because most schools pay staff salaries (§9.2 F29).
5. **Commerce settings are written through `PATCH /admin/settings`,** limited to the commerce group until M9.
6. **Every available negative entry must be in the next payout** (AC 7); payouts are recorded only (W3).
7. **Receipts are HTML with a print stylesheet** ("Save as PDF" in the browser); a server-made PDF comes later.
8. **A success after the learner already has access is an exception,** not a second enrolment.
9. **One active payment account per school;** activating another disables the old one (webhooks for the old account still resolve, so late events are processed).
10. **Receipt prefixes are not unique across schools:** receipt numbers are unique per school (`unique(tenant_id, number)`); the prefix defaults to the slug's first letters and digits.
11. **Payout methods are part of M8** (S-T12): with revenue share an instructor needs a default payout method before a paid course can be published (BR-04).
12. **Not yet:** learner refund requests (F28 SHOULD), sale prices (F24 SHOULD), settlement reconciliation (W7) and platform statements (W8, M9), automated payouts, the PDF receipt, payment-event payload purging after 2 years, and FROZEN earnings for suspended instructors (BR-28).
