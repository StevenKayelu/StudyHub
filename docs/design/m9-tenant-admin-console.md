- **Status:** DONE (2026-10-16). Items marked **PROPOSED** were decided during implementation and need client confirmation.

## 0. Gates and open decisions

- **Activation control (Q-TEN-10)** is unanswered. M9 lets the **owner go live** once the required checklist steps are done; operators can also activate. **PROPOSED.**
- **Plans and prices (Q-BIZ-8, Q-BIZ-9)** are unknown. The seed creates three plans (`starter`, `school-standard`, `marketplace`) with blueprint-default limits and `platformCommissionBps = 0`. Plans are edited in the console.
- **Retention (Q-LEG-1)** is unknown: financial records and the tenant audit log are archived at purge and kept (7 years ASSUMED); nothing deletes the archive yet.
- **Money flow (Q-TEN-4)** stays option (a) from M8; statements are invoiced outside StudyHub.
- **Custom domains (Q-TEN-5)** stay LATER: the routes exist and return `403 FEATURE_NOT_ENABLED`.

## 1. How the console sees schools (ADR-0020, PROPOSED)

The blueprint routes every console read through SECURITY DEFINER functions. M9 instead gives the console realm a **read policy on an allowlist of metadata tables** that hold no personal data, and keeps the definer inventory for cross-school _work discovery_ only:

| Table                   | Console (`app.realm = 'platform'`) | School (`app.tenant_id`)            |
| ----------------------- | ---------------------------------- | ----------------------------------- |
| `tenant`                | read; lifecycle columns writable   | its own row (`tenant_self`)         |
| `tenant_domain`         | read, add, change status           | read its own rows                   |
| `plan`                  | read and write (global table)      | read (its plan, via the tenant row) |
| `tenant_feature`        | read; `platform_override` writable | read; `enabled_by_tenant` writable  |
| `tenant_usage_daily`    | read                               | read; written by the metering job   |
| `support_access_grant`  | read; request, open, end           | read; approve, deny, revoke         |
| `domain_change_request` | read; decide                       | read; request                       |
| `platform_statement`    | read and write                     | read (owners); never written        |

- The policy is named `platform_realm` everywhere, and a CI check (T-ISO-21) fails if any other table gets one, or if an allowlisted table gains a column on the personal-data denylist (`email`, `display_name`, `phone`, `msisdn`, …).
- **Console writes that must happen inside a school** (provisioning, the owner invitation, lifecycle emails to the school's owners, statement totals) run in one transaction with `app.realm = 'platform'` **and** that school's `app.tenant_id` (`runPlatformInTenant`). They return only ids, counts and sums. **PROPOSED.**
- F43 AC 1 is checked by a **response-schema test**: every console response schema is walked and must not contain a personal field, except the documented `ownerContactEmail` (the contact staff entered at provisioning, S-C04) and the staff's own fields on `/console/me` and `/console/staff`.

## 4. PROPOSED decisions

1. Console read policies on an allowlist of metadata tables instead of one definer function per read (§1, ADR-0020).
2. Console writes inside one school run in a combined platform-and-tenant transaction and return no school data.
3. Owners can go live themselves when the required checklist steps are done (Q-TEN-10).
4. Support sessions are a separate table and cookie; every request in one is audited in both logs.
5. One `data_export` table and one worker path for report CSVs and the full export; every export is asynchronous.
6. Purge keeps the `tenant` row as a `DELETED` tombstone, archives financial records and the audit trail into `tenant_archive`, and deletes everything else.
7. Plan limits replace `DEFAULT_STORAGE_QUOTA_MB` for schools with a plan; a school without a plan (created before M9 or by the CLI) keeps every feature, has no member limits and keeps the default storage quota.
8. Staff accounts are created in the console by a platform owner with an initial password; TOTP enrolment is forced at first sign-in.
9. Statements are HTML with a print stylesheet (as receipts, M8 PROPOSED 7).
10. **Not yet:** custom domains (LATER), bulk CSV invitations, TOTP for school admins (SHOULD), learner refund requests (F28 SHOULD), a server-made PDF, the learner language switcher (only English ships), video minutes from a real provider, plan-change requests other than an email link, restoring a single school (M10 drill).
